## 1. Что такое DevOps

**DevOps** — это не программа и не одна должность, а подход: разработка (Dev) и эксплуатация (Ops) работают как одна команда, а всё, что можно автоматизировать, автоматизируется.

Раньше было так: разработчики написали код и «перекинули через забор» админам, а админы вручную ставили его на сервера. Получалось медленно, с ошибками, и никто ни за что не отвечал целиком.

DevOps-инженер строит **конвейер**, по которому код сам проходит путь от коммита до работающего сервиса:

```
  код → сборка → тесты → упаковка → доставка на сервер → работа → мониторинг
   ↑                                                                      │
   └──────────────── обратная связь: метрики, логи, алерты ←─────────────┘
```

Основные навыки DevOps-инженера — ровно то, что мы будем изучать:

| Навык | Что это | Инструменты в проекте |
|---|---|---|
| Linux и сети | Фундамент: почти все серверы работают на Linux | Ubuntu (WSL), Debian (Proxmox), SSH |
| Контроль версий | Всё хранится в Git: код, конфиги, инфраструктура | Git, GitHub |
| Виртуализация | Много изолированных машин на одном железе | Proxmox VE |
| Инфраструктура как код (IaC) | Серверы описываются файлами, а не создаются руками | Terraform / OpenTofu, Ansible |
| Контейнеры | Приложение упаковано со всеми зависимостями | Docker |
| Оркестрация | Управление множеством контейнеров на многих машинах | Kubernetes |
| CI/CD | Автоматическая сборка и выкатка | GitHub Actions, Argo CD |
| Наблюдаемость (observability) | Видеть, что происходит внутри системы | Prometheus, Grafana, Loki |
| Безопасность | Ключи, доступы, секреты, бэкапы | SSH-ключи, Cloudflare Access, бэкапы |

│  Proxmox VE (гипервизор)  +  cloudflared (туннель)                │
│                                                                   │
│   ┌── VM: k8s control plane ──┐  ┌── VM: k8s worker ─┐  ┌── VM ──┐ │
│   │                           │  │                   │  │  ...   │ │
│   └───────────────────────────┘  └───────────────────┘  └────────┘ │
│                ▲ кластер Kubernetes                               │
│                │  внутри: приложение, Prometheus, Grafana, Loki    │
└────────────────┼──────────────────────────────────────────────────┘

Главная идея: **ноутбук — пульт управления, сервер — полигон, GitHub — память проекта.** Если сервер сгорит, всё должно подниматься заново из кода в GitHub.

## 3. Слой за слоем

### 3.1. Рабочая станция (ОС-инструмент)

- **Windows 11 на внешнем SSD** — изолированная рабочая среда. Основную систему ноутбука не трогаем.
- **WSL2 (Windows Subsystem for Linux)** — настоящее ядро Linux, работающее внутри Windows в лёгкой виртуальной машине. Нужно потому, что почти все DevOps-инструменты родом из Linux и там работают лучше всего (Ansible, например, вообще не работает на Windows как управляющая машина).
- **Терминал и оболочка (shell).** Терминал — окно, оболочка — программа, которая понимает команды. В Windows это **PowerShell**, в Linux — **bash**. Синтаксис у них разный, поэтому в инструкциях всегда указывается, где выполнять команду.
- **Менеджер пакетов** — программа, которая ставит другие программы из проверенного каталога одной командой: `winget` в Windows, `apt` в Ubuntu/Debian. Установку командами можно записать в скрипт и повторить, а клики мышью — нельзя.
- **VS Code** — редактор. Расширения Remote-WSL и Remote-SSH позволяют редактировать файлы внутри Linux или на сервере так, будто они лежат локально.

**Правило WSL:** проекты храни в домашней папке Linux (`~` = `/home/yarik`), а не в `/mnt/c/...`. Через `/mnt/c` работа идёт медленно, и бывают проблемы с правами.

### 3.2. Удалённый доступ: SSH и ключи

**SSH** — защищённый протокол для удалённого управления. Ты вводишь команды в своём терминале, а выполняются они на сервере.

**Ключи вместо паролей.** Это асимметричная криптография:
- **приватный ключ** (`id_ed25519`) — как физический ключ от двери. Никогда никому не передаётся;
- **публичный ключ** (`id_ed25519.pub`) — как замок. Его можно спокойно раздавать: GitHub, серверам.

Сервер проверяет, что у тебя есть ключ, подходящий к его замку, и при этом сам ключ по сети не передаётся.

- **Passphrase** — пароль на приватный ключ. Если украдут файл ключа, без пароля он бесполезен.
- **ssh-agent / keychain** — держат расшифрованный ключ в памяти, чтобы не вводить пароль каждый раз.
- **known_hosts и fingerprint** — при первом подключении сервер показывает «отпечаток» своего ключа. Сверив его, ты убеждаешься, что подключился к настоящему серверу, а не к подмене (атака «человек посередине»). Отпечаток запоминается в `~/.ssh/known_hosts`.

### 3.3. Git и GitHub

**Git** — система контроля версий. Хранит историю всех изменений: кто, когда и что поменял, и позволяет вернуться к любой точке.

| Понятие | Что это |
|---|---|
| **Репозиторий (repo)** | Папка проекта вместе со всей историей |
| **Коммит (commit)** | Сохранённый «снимок» изменений с описанием |
| **Ветка (branch)** | Параллельная линия разработки. `main` — основная |
| **Merge** | Слияние одной ветки в другую |
| **Remote** | Копия репозитория на сервере (у нас GitHub), обычно называется `origin` |
| **clone / pull / push** | Скачать репозиторий / забрать новые изменения / отправить свои |
| **Pull Request (PR)** | Запрос «влей мою ветку в main», с обсуждением и ревью |
| **.gitignore** | Список файлов, которые Git не должен отслеживать (секреты, мусор) |

Базовый цикл работы: `git status → git add → git commit → git push`.

**GitHub** — хостинг для Git-репозиториев плюс задачи, ревью и CI/CD (GitHub Actions). Для тебя это ещё и **портфолио**: работодатель смотрит на твои репозитории.

**Правило №1:** секреты (пароли, токены, приватные ключи) **никогда** не попадают в Git. Даже если удалить файл потом, он остаётся в истории.

### 3.4. Сеть (минимум, который нужен)

- **IP-адрес** — адрес устройства в сети. **Локальный** (`192.168.x.x`) работает только дома.
- **Белый IP** — публичный адрес, по которому к тебе можно подключиться из интернета. **Серый IP** — когда провайдер прячет тебя за общим адресом (NAT), и снаружи подключиться напрямую нельзя. У тебя серый, поэтому нужен туннель.
- **Порт** — «дверь» конкретного сервиса на машине: SSH — 22, HTTP — 80, HTTPS — 443, веб-интерфейс Proxmox — 8006.
- **DNS** — «телефонная книга» интернета: переводит имя (`example.com`) в IP-адрес.
- **Cloudflare Tunnel (`cloudflared`)** — программа на сервере сама устанавливает **исходящее** соединение до Cloudflare. Когда ты открываешь свой домен, Cloudflare пересылает запрос по этому туннелю. Так работает даже при сером IP, и порты наружу открывать не нужно.
- **Cloudflare Zero Trust Access** — дополнительная «проходная» перед сервисом: сначала вход через Cloudflare (почта, код, 2FA), и только потом доступ к Proxmox. Это настроим, когда вернёмся к серверу.
- **VPN (WireGuard, Tailscale)** — запасной канал: ноутбук как будто подключён к домашней сети, где бы ты ни был.
- **Bridge (`vmbr0` в Proxmox)** — виртуальный коммутатор, через который виртуальные машины выходят в домашнюю сеть.

### 3.5. Виртуализация: Proxmox VE

- **Гипервизор** — программа, которая делит одно физическое железо на несколько виртуальных машин (VM). У каждой VM своя ОС, своя память и диск, и они не мешают друг другу.
  - **Type 1** (bare metal) — ставится прямо на железо вместо обычной ОС. Proxmox, VMware ESXi.
  - **Type 2** — работает поверх обычной ОС. VirtualBox, VMware Workstation.
- **Proxmox VE** — бесплатный гипервизор Type 1 на базе Debian Linux. Внутри использует **KVM/QEMU** для виртуальных машин и **LXC** для контейнеров.
- **VM или LXC-контейнер.** VM — полноценный компьютер со своим ядром: тяжелее, но полностью изолирован. LXC делит ядро с хостом: легче, быстрее, но изоляция слабее. Для Kubernetes обычно используют VM.
- **Шаблон (template) и cloud-init.** Готовую «заготовку» VM клонируют сколько угодно раз, а **cloud-init** при первом запуске клона задаёт имя, IP, пользователя и SSH-ключ. Так создание VM занимает секунды, и его можно автоматизировать.
- **Снапшот (snapshot)** — мгновенный «снимок» состояния VM. Сломал что-то — откатился. Снапшот **не является бэкапом**: он лежит на том же диске.
- **Хранилище:** **LVM-thin** — простой вариант, **ZFS** — продвинутый (снапшоты, проверка целостности), но любит много RAM.

**Ограничения нашего железа.** 16 ГБ RAM и один HDD — это немного. Kubernetes на 2–3 VM плюс мониторинг займут почти всю память, а HDD медленный при одновременной нагрузке от нескольких VM. Будем планировать ресурсы аккуратно и выбирать лёгкие варианты.

### 3.6. Инфраструктура как код (IaC)

**Идея:** вместо того чтобы кликать в интерфейсе, ты описываешь инфраструктуру в текстовых файлах и хранишь их в Git. Инструмент сам приводит реальность к описанию.

- **Императивно** — «сделай шаг 1, потом шаг 2» (обычный скрипт).
- **Декларативно** — «хочу, чтобы было так» (Terraform, Kubernetes). Инструмент сам вычисляет, какие шаги нужны.
- **Идемпотентность** — запусти хоть 10 раз, результат одинаковый. Если всё уже в нужном состоянии, ничего не меняется. Ключевое свойство хорошей автоматизации.

| Инструмент | Задача | Аналогия |
|---|---|---|
| **Terraform / OpenTofu** | **Создаёт** ресурсы: VM, диски, сети, DNS-записи | Строитель: возводит дом |
| **Ansible** | **Настраивает** то, что создано: ставит пакеты, правит конфиги, запускает сервисы | Отделочник: проводит свет, ставит мебель |

**Terraform:**
- **provider** — плагин для конкретной платформы (у нас — для Proxmox, позже для Cloudflare);
- **state** — файл, где Terraform помнит, что он уже создал;
- **`terraform plan`** — показать, что изменится; **`terraform apply`** — применить.
- **OpenTofu** — открытый форк Terraform, появившийся после смены лицензии Terraform. Команды и синтаксис почти одинаковые.

**Ansible:**
- **agentless** — на серверы ничего не ставится, Ansible ходит туда по SSH;
- **inventory** — список серверов;
- **playbook** — YAML-файл со сценарием настройки;
- **role** — переиспользуемый блок (например, «поставить Docker»).

### 3.7. Контейнеры: Docker

**Проблема:** «у меня работает, а на сервере нет» — разные версии библиотек, настроек, ОС.
**Решение:** упаковать приложение вместе со всем, что ему нужно, в **контейнер**.

| Понятие | Что это | Аналогия |
|---|---|---|
| **Dockerfile** | Рецепт сборки образа | Рецепт |
| **Образ (image)** | Собранный неизменяемый шаблон | Замороженное блюдо |
| **Контейнер** | Запущенный экземпляр образа | Разогретая порция |
| **Registry** | Хранилище образов (Docker Hub, GitHub Container Registry) | Склад |
| **Docker Compose** | Запуск нескольких связанных контейнеров одним YAML-файлом | Меню комплексного обеда |

**Контейнер или VM:** контейнер делит ядро ОС хоста, поэтому запускается за секунды и весит мегабайты. VM эмулирует целый компьютер.

### 3.8. Kubernetes (k8s)

Docker запускает контейнеры на **одной** машине. **Kubernetes** управляет контейнерами на **многих** машинах: сам решает, где запустить, перезапускает упавшие, масштабирует, раздаёт трафик.

Главный принцип: ты описываешь **желаемое состояние** («хочу 3 копии приложения»), а Kubernetes постоянно сравнивает его с реальностью и исправляет расхождения.

**Архитектура:**
- **Кластер** — вся система целиком;
- **Нода (node)** — машина в кластере (у нас — VM в Proxmox);
- **Control plane** — «мозг»: принимает команды, хранит состояние (в базе **etcd**), решает, где что запускать;
- **Worker** — ноды, где реально работают приложения.

**Основные объекты:**

| Объект | Что делает |
|---|---|
| **Pod** | Минимальная единица: один или несколько контейнеров, работающих вместе |
| **Deployment** | «Держи N копий этого пода, обновляй их плавно» |
| **Service** | Постоянный адрес для группы подов (поды умирают и меняют IP, а Service остаётся) |
| **Ingress** | Вход снаружи по HTTP: какой домен или путь на какой Service вести |
| **Namespace** | «Папка» для разделения ресурсов (например, `monitoring`, `app`) |
| **ConfigMap / Secret** | Настройки и секреты, которые передаются в поды |
| **PersistentVolume (PV / PVC)** | Постоянное хранилище: данные переживают перезапуск пода |

**Инструменты:**
- **kubectl** — главная утилита управления кластером;
- **kubeconfig** — файл с адресом кластера и ключами доступа (`~/.kube/config`);
- **Helm** — менеджер пакетов для Kubernetes. **Chart** — готовый пакет, например «Prometheus целиком одной командой»;
- **k9s** — удобный интерфейс к кластеру прямо в терминале.

**Способы установки кластера:**
- **kubeadm** — «честная» установка, как в продакшене. Сложнее, но учит, как всё устроено;
- **k3s** — облегчённый Kubernetes одним бинарником. Мало ест, отлично подходит для слабого железа.

### 3.9. CI/CD и GitOps

- **CI (Continuous Integration)** — при каждом пуше автоматически собрать проект и прогнать тесты.
- **CD (Continuous Delivery / Deployment)** — автоматически доставить результат на сервер.
- **Pipeline** — цепочка шагов (сборка → тесты → сборка образа → деплой). **GitHub Actions** описывает её YAML-файлом прямо в репозитории; **runner** — машина, которая выполняет шаги.
- **GitOps** — следующий шаг: состояние кластера целиком описано в Git, а **Argo CD** или **Flux** внутри кластера сами подтягивают изменения. Хочешь что-то поменять в кластере — делаешь коммит, а не команду руками.

### 3.10. Наблюдаемость (observability)

Три «столпа»:

| Что | Вопрос | Инструменты |
|---|---|---|
| **Метрики** | «Сколько?» — загрузка CPU, память, число запросов, ошибки | Prometheus |
| **Логи** | «Что именно произошло?» — текстовые записи событий | Loki (+ сборщик Grafana Alloy, раньше Promtail) или ELK |
| **Трейсы** | «Где тормозит запрос?» — путь запроса через сервисы | Tempo, Jaeger (позже, по желанию) |

- **Prometheus** — сам опрашивает (**pull**) сервисы и собирает числовые метрики. **Exporter** — программа, которая отдаёт метрики в его формате (`node_exporter` — метрики машины). Язык запросов — **PromQL**.
- **Grafana** — дашборды: красивые графики по данным из Prometheus и Loki.
- **Alertmanager** — отправляет **алерты** (уведомления в Telegram или на почту), когда что-то идёт не так.
- **Loki** — хранилище логов от создателей Grafana, лёгкое и дешёвое. **ELK** (Elasticsearch + Logstash + Kibana) — мощнее, но слишком тяжёл для 16 ГБ.

### 3.11. Безопасность и бэкапы

- **Принцип наименьших привилегий** — давать только тот доступ, который нужен.
- **Секреты** — не в Git. Позже: **SOPS** (шифрованные файлы в Git) или **Vault**.
- **2FA** — везде, где возможно (GitHub, Cloudflare).
- **Бэкапы и правило 3-2-1:** 3 копии данных, на 2 разных носителях, 1 — вне дома. Снапшот — не бэкап. Бэкап, который ни разу не пробовали восстановить, — тоже не бэкап.
- **Образ диска ОС-инструмента** — снять, когда система будет настроена.
- **BitLocker** — шифрование внешнего SSD на случай потери.

## 5. Как учиться

1. **Сначала руками, потом автоматизировать.** Нельзя автоматизировать то, чего не понимаешь.
2. **Перед командой — понять, что она делает.** Если непонятно, спроси или посмотри `man <команда>` / `<команда> --help`.
3. **Ломать и чинить.** Для этого и нужен хомлаб. Перед экспериментом — снапшот.
4. **Документировать.** Каждый этап — заметка в репозитории. Это и память, и портфолио.
5. **Читать ошибки целиком.** В 90% случаев ответ написан в последних строках вывода.

## 6. Сленг

| Слово | Значение |
|---|---|
| **Прод (production)** | Боевая среда, с которой работают реальные пользователи |
| **Стейдж, дев (staging, dev)** | Тестовые среды перед продом |
| **Деплой, задеплоить, раскатить** | Выкатить новую версию на сервер |
| **Откатить (rollback)** | Вернуть предыдущую версию |
| **Релиз** | Выпуск версии |
| **Билд** | Сборка проекта |
| **Артефакт** | Результат сборки (файл, образ) |
| **Пайплайн** | Автоматическая цепочка шагов CI/CD |
| **Закоммитить, запушить, спуллить** | git commit / push / pull |
| **Смержить** | Слить ветку (merge) |
| **PR / MR** | Pull Request (GitHub) / Merge Request (GitLab) — запрос на слияние |
| **Ревью, апрув** | Проверка кода коллегой / одобрение |
| **Хотфикс** | Срочное исправление в проде |
| **Легаси** | Старый код или система, которую страшно трогать |
| **Инфра** | Инфраструктура |
| **Конфиг** | Файл настроек |
| **Кубер, k8s** | Kubernetes (8 букв между «k» и «s») |
| **Нода, под, неймспейс** | Node, Pod, Namespace в Kubernetes |
| **Чарт, хельм** | Helm-пакет |
| **Образ, имадж** | Docker image |
| **Реджистри** | Хранилище образов |
| **Кронджоба** | Задача по расписанию (cron job) |
| **Алерт** | Автоматическое уведомление о проблеме |
| **Дежурство, он-колл** | Дежурный инженер, которого будят при аварии |
| **Инцидент** | Авария или сбой |
| **Постмортем** | Разбор инцидента: что случилось, почему, как не допустить снова (без поиска виноватых) |
| **Аптайм / даунтайм** | Время работы / простоя |
| **SLA / SLO / SLI** | Обещание клиенту / внутренняя цель / измеряемый показатель надёжности |
| **Скейлинг** | Масштабирование: горизонтальное — больше копий, вертикальное — больше ресурсов одной машине |
| **Балансер** | Балансировщик нагрузки: распределяет запросы между копиями |
| **Прокси, реверс-прокси** | Посредник между клиентом и сервисом (nginx, Traefik) |
| **Бастион, джамп-хост** | Единственная машина, через которую заходят на остальные |
| **Идемпотентность** | Повторный запуск не меняет результат |
| **Дрифт** | Реальная инфраструктура разошлась с описанием в коде (кто-то поменял руками) |
| **Pets vs cattle** | «Питомцы» — уникальные серверы, которые лечат вручную; «скот» — одинаковые, сломался — пересоздали. DevOps стремится ко второму |
| **Bare metal** | Физический сервер без виртуализации |
| **Хомлаб** | Домашняя лаборатория — то, что ты строишь |
| **«На моей машине работает»** | Классическая проблема, которую решают контейнеры |
| **«Не деплой в пятницу»** | Народная мудрость: если сломается, чинить придётся в выходные |
| **YAML-инженер** | Шутка: DevOps пишет больше YAML, чем кода |
